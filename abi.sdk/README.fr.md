# Suite de SDKs de collecte de données multilingue ABI (`abi.sdk`)

**Langue / Language**: [简体中文](README.md) | [繁體中文](README.zh-TW.md) | [English](README.en.md) | [日本語](README.ja.md) | [한국어](README.ko.md) | [Español](README.es.md) | [Português](README.pt.md) | [Deutsch](README.de.md) | **[Français](README.fr.md)** | [Русский](README.ru.md) | [Tiếng Việt](README.vi.md) | [ไทย](README.th.md) | [Bahasa Indonesia](README.id.md)

`abi.sdk` fournit des SDKs de collecte de données de niveau production pour les clients et les serveurs, destinés à la plateforme d'analyse du comportement utilisateur (User Behavior Analytics, UBA) et de Business Intelligence (BI) ABI. Étalonnée sur la [spécification ThinkingData SDK v3.4](https://docs.thinkingdata.cn/ta-manual/v3.4/installation/installation_menu/installation_menu.html), cette suite aligne rigoureusement les protocoles filaires de communication, la cartographie de double identité (Dual-ID) et la validation des schémas avec la passerelle d'ingestion ABI [`abi.srv`](../abi.srv/) (`:8081`) et les moteurs de traitement de flux [`abi.flink`](../abi.flink/) (Job1 ETL temps réel et Job2 ingestion ODS brute).

## 2. Protocole filaire de lot de la passerelle d'ingestion (`POST /collect/api/v1/track/batch`)

Tous les consommateurs HTTP clients et serveurs transmettent une charge utile JSON standardisée par lot à la passerelle d'ingestion :

```json
{
  "project_id": 1,
  "project_token": "abi_tok_...",
  "debug": false,
  "dry_run": false,
  "events": [
    {
      "event_id": "018f6b9c-7c40-7000-8000-000000000001",
      "event_name": "OrderPaid",
      "distinct_id": "vis_device_001",
      "login_id": "user_10001",
      "timestamp": 1731174000000,
      "properties": {
        "$lib": "abi-ios-sdk",
        "$lib_version": "1.0.0",
        "$os": "iOS",
        "$app_version": "2.1.0",
        "$duration": 12.345,
        "amount": 199.0,
        "order_id": "9007199254740993"
      }
    }
  ]
}
```

### 2.1 Contraintes de double identité (Dual-ID) et d'idempotence alignées sur ThinkingData

- **`distinct_id` (Identifiant Visiteur / Appareil)** : L'identifiant unique du visiteur ou de l'appareil client sur le protocole réseau. Les caractères de contrôle ASCII (`0x00–0x08`, `0x0E–0x1F`, `0x7F`) sont rejetés, les espaces blancs Unicode en début/fin sont nettoyés et la longueur maximale en octets UTF-8 est de **64 octets**. Les SDKs clients génèrent et persistent automatiquement `distinct_id` localement (modifiable via `identify(visitorId)`) ; les SDKs serveurs peuvent transmettre une chaîne vide `""` lors de l'envoi d'événements de compte purs portant déjà un `login_id` non vide (**ne jamais copier ni tronquer `login_id` dans `distinct_id`**).
- **`login_id` (Identifiant de Compte Authentifié)** : L'identifiant du compte métier authentifié ; sa longueur maximale en octets UTF-8 est de **128 octets** (omis ou `""` pour les visiteurs non authentifiés). Au moins l'un des deux identifiants `distinct_id` ou `login_id` **doit être non vide** pour chaque événement.
- **`login()` client purement local et mappage d'identités Flink automatique** : L'appel de `login(accountId)` sur les SDKs clients **met à jour exclusivement `login_id` dans l'état local**, sans écraser `distinct_id` et sans émettre d'événement système distinct de liaison d'identité ; l'appel de `logout()` réinitialise `login_id` tout en conservant le `distinct_id` actuel. Sur les SDKs clients comme serveurs, **dès qu'un événement comportemental (`Track*`) ou une opération de profil (`$user_*`) transporte à la fois un `distinct_id` et un `login_id` non vides**, Flink Job1 les associe automatiquement en temps réel dans `abi.identity_map`.
- **`event_id` (Clé primaire idempotente)** : Longueur maximale en octets UTF-8 de **64 octets**. Préservée lors des réessais hors-ligne en cas de panne réseau, de code HTTP `429` ou de réponses `5xx` afin de garantir une ingestion idempotente. (*Remarque : Selon la règle D7① / porte G6, la déduplication trackFirst et les événements modifiables via trackUpdate/trackOverwrite sont marqués comme non pris en charge dans la version actuelle ; pour garantir l'idempotence, transmettez un event_id fixe et déterministe dans track au sein de la même fenêtre de partition*).

### 2.2 Protection de précision des grands entiers ($> 2^{53}-1$)

JavaScript et les analyseurs JSON standards utilisent des nombres à virgule flottante en double précision IEEE-754 avec un entier sécurisé maximal de $2^{53}-1$ (`9007199254740991`).

- Dès que la valeur absolue d'une propriété entière dépasse `9007199254740991` (par exemple, les identifiants de commande Snowflake 64 bits tels que `9007199254740993` ou `Int64.min` / `Long.MIN_VALUE`), chaque SDK ABI la sérialise automatiquement sous forme de chaîne décimale (`"9007199254740993"`) afin d'éviter toute troncature des bits de poids faible.
- Tous les SDKs rejettent également `NaN`, `Infinity` / `-Infinity`, les éléments de liste `null`, ainsi que les objets/tableaux imbriqués à l'intérieur des propriétés de liste avant toute mise en file d'attente.

### 2.3 Opérations sur les profils utilisateurs `$user_*`

Tous les SDKs mettent à disposition 7 méthodes standard de mutation de profil utilisateur, acheminées vers la table à clé primaire StarRocks `abi.dim_users` :

| Méthode SDK | Valeur filaire `event_name` | Sémantique de mutation du profil |
|------------|-------------------|----------------------------|
| `userSet(props)` | `$user_set` | Écrase les propriétés de profil les plus récentes (insertion si absentes, mise à jour si présentes) |
| `userSetOnce(props)` | `$user_set_once` | Initialise les propriétés de profil uniquement si elles sont actuellement nulles (ex. premier canal d'acquisition, source d'inscription) |
| `userAdd(props)` | `$user_add` | Incrémente/décrémente de manière atomique les propriétés de profil numériques (ex. points de fidélité, dépenses cumulées) |
| `userUnset(keys)` | `$user_unset` | Efface les colonnes de propriétés spécifiées du profil utilisateur (`NULL` dans `dim_users`) |
| `userAppend(props)` | `$user_append` | Ajoute des éléments aux propriétés de profil de type tableau/liste |
| `userUniqAppend(props)` | `$user_uniq_append` | Ajoute des éléments aux propriétés de profil de type tableau/liste avec déduplication automatique |
| `userDelete()` | `$user_del` | Supprime la ligne de profil de l'utilisateur actuel de `abi.dim_users` (`StarRocksSinkOP.DELETE`) tout en préservant les événements comportementaux historiques dans `dwd_events` |

> **Règle d'isolation** : Lors de la construction d'événements `$user_*` (ou `#user_*`), les SDKs **n'injectent jamais** de super propriétés statiques/dynamiques ni de propriétés d'environnement prédéfinies (`$os`, `$app_version`, `$lib`), empêchant ainsi les métadonnées d'environnement de polluer la table `abi.dim_users`.

### 2.4 Guide pour les ingénieurs d'intégration : Exigences des champs et responsabilités Client vs Serveur (Important)

Dans les architectures de production, les **SDKs côté client (Web / Mini-programme / Application mobile)** et les **SDKs côté serveur (Go / Java)** opèrent au sein de topologies réseau fondamentalement différentes. Les ingénieurs d'intégration doivent être attentifs aux distinctions de responsabilités pour chaque champ selon le scénario :

| Champ / Propriété | SDKs Client (`ts-web` / `mobile` Flutter·Android·iOS) | SDKs Serveur (`go` / `java` / `python` / `nodejs` / `csharp` / `php` / `ruby`) | HTTP direct (`RESTFUL_API.md`) | Comportement Passerelle (`:8081`) et ETL Flink |
| :--- | :--- | :--- | :--- | :--- |
| **`project_id` & `project_token`** | **Requis une seule fois à `init()`** | **Requis lors de l'initialisation du Consumer** | **Requis au niveau supérieur de chaque requête** | La passerelle valide le statut et le jeton du projet ; renvoie `401/403` si invalide |
| **`event_name`** | **Requis sur chaque appel `track()`** (automatiquement défini à `$user_*` par `userSet*()`) | **Requis sur chaque appel `Track()`** (automatiquement défini à `$user_*` par `UserSet*()`) | **Requis sur chaque événement** | Validé pour `<= 128` caractères et le format `^[A-Za-z_][A-Za-z0-9_]*$` (ou liste blanche système `$`/`#`) |
| **Identité utilisateur (`distinct_id` / `login_id`)** | **Géré automatiquement (non transmis par `track`)** : Le SDK génère et stocke le `distinct_id` visiteur à `init()` ; le développeur appelle `login(accountId)` pour enregistrer localement `login_id` (les événements suivants portent automatiquement les deux identifiants) | **Requis à CHAQUE appel** : Le SDK serveur est un singleton sans état partagé entre tous les utilisateurs ; le développeur **doit explicitement transmettre** `login_id` (`accountId`) et/ou le `distinct_id` visiteur transmis par le client (au moins un non vide ; ne jamais copier `login_id` dans `distinct_id`) | **Requis sur chaque événement** (au moins l'un des deux `distinct_id` / `login_id` doit être non vide) | La passerelle rejette les identités vides (`missing_identity`) ; dès qu'un événement porte à la fois un `distinct_id` et un `login_id` non vides, Flink les associe automatiquement dans `abi.identity_map` |
| **IP publique de l'utilisateur final (`#ip` / `$ip`)**<br/>*(Utilisée pour la géolocalisation Pays / Province ou Région / Ville GeoIP)* | **NE PAS transmettre (le client ne peut pas l'obtenir de manière fiable)** : Les navigateurs et applications mobiles sont derrière un NAT ; la passerelle extrait automatiquement l'IP client de la connexion HTTP | **DOIT être transmise par le serveur** : Lorsque les backends Go/Java appellent la passerelle, l'IP TCP vue par la passerelle est l'**IP du centre de données / VPC du backend** (ou aucune pour `LoggerConsumer`). Les ingénieurs serveur doivent extraire la véritable IP utilisateur des en-têtes clients (`X-Forwarded-For` / `X-Real-IP`) et la transmettre dans `properties["#ip"]` ou `"$ip"` | Omettre pour les appels directs des clients ; **transmettre `"#ip"` ou `"$ip"` dans `properties` pour les appels serveur à serveur** | Flink résout la GeoIP selon la priorité stricte **`properties["#ip"]` > `properties["$ip"]` > `client_ip` du socket passerelle**, valide le format IP numérique et retire `#ip`/`$ip` des `properties` |
| **Horodatage de l'événement (`timestamp` / `#time` / `$time`)** | **Rempli automatiquement (`Date.now()`)** : Omettre pour les événements en temps réel ; ne transmettre `#time` / `$time` ou `options.timestamp` que lors du rattrapage d'événements historiques hors-ligne | **Automatique pour le temps réel / Requis pour l'asynchrone et le rattrapage** : Pour les consommateurs de files d'attente différées, webhooks de paiement ou imports historiques, transmettre explicitement l'heure métier réelle via `properties["#time"]` (ou `TrackOptions.Timestamp` / `Date` / `Instant`) | **Requis sur chaque événement** (soit le champ `timestamp` en millisecondes au niveau racine, soit `properties["#time"]` / `"$time"`) | Les SDKs et la passerelle extraient `#time` / `$time` dans le champ `timestamp` racine en ms et les retirent des `properties` ; validation selon `ts_window_days` |
| **Clé d'idempotence (`event_id`)** | **Générée automatiquement (UUIDv4)** : Conservée automatiquement lors des réessais hors-ligne ; conformément à la règle D7① / porte G6, `trackFirst`/`trackUpdate`/`trackOverwrite` sont considérés comme non pris en charge dans la version actuelle | **Générée automatiquement par défaut / Recommandée pour les transactions** : Transmettez une clé métier déterministe (ex. `"ord_paid_" + orderNo`) via `TrackWithOptions` / `trackWithId` pour éviter tout double comptage lors des réessais de files MQ | Recommandé (la passerelle génère un UUID si omis, mais les réessais sans `event_id` fixe ne seront pas dédupliqués) | La table StarRocks `dwd_events` utilise `event_id` pour la déduplication idempotente |
| **Contexte de l'appareil (`$os` / `$app_version` / `$screen_width`, etc.)** | **Collecté et injecté automatiquement par le SDK** (dans les événements comportementaux uniquement ; exclu de `$user_*`) | **Non disponible sur le serveur** : Définir les métadonnées de service via `SetSuperProperties`, ou transmettre les en-têtes du client (`$os`, `$app_version`, `$device_model`) dans `properties` | Transmettre explicitement dans `properties` selon les besoins | Flink promeut `$os`, `$app_version`, `$device_model`, etc. en colonnes physiques dans `dwd_events` |

> **Bonne pratique de réconciliation des entonnoirs Frontend + Backend** : Lors de la combinaison de la navigation côté client (SDK Web/App) avec le traitement des commandes côté serveur (SDK Go/Java/Python/Node/C#/PHP/Ruby), transmettez l'ID visiteur du client (`abi.getDistinctId()`) à votre API backend (par ex. via l'en-tête de requête `X-ABI-Distinct-Id`). Le backend transmet ensuite à la fois le `loginId` (`accountId`), le `distinctId` visiteur et le véritable `"#ip"` de l'utilisateur lors de l'appel au SDK serveur. Flink relie automatiquement les deux identifiants sur n'importe quel événement, assurant ainsi une attribution fluide de l'entonnoir multi-terminaux et une géolocalisation précise.

## 3. Démos interactives en deux étapes et Référence rapide des exemples de code

Toutes les démonstrations d'interface graphique et les démos CLI/méthodes au sein de `abi.sdk` suivent un **flux de travail unifié en deux étapes** :
1. **Étape 1 (Configuration des paramètres et aperçu JSON de la requête unique en direct)** : La modification de l'identité, des super propriétés ou des paramètres d'événement met à jour sur place un **aperçu JSON concret du corps de requête `POST /collect/api/v1/track/batch`** (sans générer une multitude de cartes de journaux superflues).
2. **Étape 2 (Confirmation explicite et soumission)** : Le clic sur **Confirmer et Soumettre** (`确认提交`) ou la confirmation dans la CLI transmet cette charge utile exacte et affiche la réponse la plus récente de la passerelle.

| Plateforme / SDK | Point d'entrée de la démo exécutable / UI interactive | Source principale du SDK | Commande de vérification et de lancement |
