# Suite de SDKs de Coleta de Dados Multilinguagem ABI (`abi.sdk`)

**Idioma / Language**: [简体中文](README.md) | [繁體中文](README.zh-TW.md) | [English](README.en.md) | [日本語](README.ja.md) | [한국어](README.ko.md) | [Español](README.es.md) | **[Português](README.pt.md)** | [Deutsch](README.de.md) | [Français](README.fr.md) | [Русский](README.ru.md) | [Tiếng Việt](README.vi.md) | [ไทย](README.th.md) | [Bahasa Indonesia](README.id.md)

O `abi.sdk` fornece SDKs de coleta de dados de nível de produção para clientes e servidores da plataforma de Análise de Comportamento do Usuário (UBA) e Business Intelligence (BI) do ABI. Tomando como referência a [especificação ThinkingData SDK v3.4](https://docs.thinkingdata.cn/ta-manual/v3.4/installation/installation_menu/installation_menu.html), esta suíte alinha rigorosamente os contratos de comunicação em rede (wire format), o mapeamento de dupla identidade e a validação de esquemas com o Gateway de Ingestão ABI [`abi.srv`](../abi.srv/) (`:8081`) e os motores de streaming [`abi.flink`](../abi.flink/) (Job1 ETL em tempo real e Job2 ingestão ODS bruta).

## 2. Contrato de Transmissão em Lote do Gateway de Ingestão (`POST /collect/api/v1/track/batch`)

Todos os consumidores HTTP de cliente e servidor enviam uma carga útil JSON em lote padronizada para o gateway de ingestão:

```json
{
  "project_id": 1,
  "project_token": "abi_tok_...",
  "debug": false,
  "dry_run": false,
  "events": [
    {
      "event_id": "018f6b9c-7c40-7000-8000-000000000001",
      "event_name": "OrderPaid",
      "distinct_id": "vis_device_001",
      "login_id": "user_10001",
      "timestamp": 1731174000000,
      "properties": {
        "$lib": "abi-ios-sdk",
        "$lib_version": "1.0.0",
        "$os": "iOS",
        "$app_version": "2.1.0",
        "$duration": 12.345,
        "amount": 199.0,
        "order_id": "9007199254740993"
      }
    }
  ]
}
```

### 2.1 Restrições de Dupla Identidade e Idempotência Alinhadas ao ThinkingData

- **`distinct_id` (ID de Visitante / Dispositivo)**: O único identificador de visitante ou dispositivo cliente transmitido na rede. Caracteres de controle ASCII (`0x00–0x08`, `0x0E–0x1F`, `0x7F`) são rejeitados, espaços em branco Unicode no início/fim são removidos e o comprimento máximo em bytes UTF-8 é de **64 bytes**. Os SDKs de cliente geram e persistem `distinct_id` localmente de forma automática (substituível via `identify(visitorId)`); os SDKs de servidor podem enviar uma string vazia `""` ao reportar eventos de conta pura que já contenham um `login_id` não vazio (**nunca copie ou truncar `login_id` em `distinct_id`**).
- **`login_id` (ID de Conta Autenticada)**: O identificador de conta de negócio autenticada; o comprimento máximo em bytes UTF-8 é de **128 bytes** (omitido ou `""` para visitantes não autenticados). Pelo menos um entre `distinct_id` ou `login_id` **deve ser não vazio** em cada evento.
- **`login()` Puramente Local no Cliente e Mapeamento Automático de IDs no Flink**: Chamar `login(accountId)` nos SDKs de cliente **estritamente atualiza `login_id` no estado local** sem sobrescrever `distinct_id` e sem emitir um evento de sistema de vinculação de identidade separado; chamar `logout()` limpa `login_id` enquanto mantém o `distinct_id` atual. Em ambos os SDKs de cliente e servidor, **sempre que qualquer evento de comportamento (`Track*`) ou operação de perfil (`$user_*`) contiver tanto `distinct_id` quanto `login_id` não vazios**, o Flink Job1 unifica-os automaticamente em `abi.identity_map` em tempo real.
- **`event_id` (Chave Primária Idempotente)**: O comprimento máximo em bytes UTF-8 é de **64 bytes**. Preservado durante repetições offline em falhas de rede, respostas HTTP `429` ou `5xx` para garantir ingestão idempotente. (*Nota: De acordo com o controle D7① / G6, a desduplicação com trackFirst e eventos mutáveis trackUpdate/trackOverwrite não são suportados na versão atual; para garantir idempotência, envie um event_id determinístico fixo em track dentro da mesma janela de partição*).

### 2.2 Proteção de Precisão para Inteiros Grandes ($> 2^{53}-1$)

O JavaScript e os analisadores JSON padrão utilizam números de ponto flutuante de precisão dupla IEEE-754 com limite seguro máximo de $2^{53}-1$ (`9007199254740991`).

- Sempre que o valor absoluto de uma propriedade inteira exceder `9007199254740991` (por exemplo, IDs de pedido Snowflake de 64 bits como `9007199254740993` ou `Int64.min` / `Long.MIN_VALUE`), cada SDK ABI o serializa automaticamente como uma string decimal (`"9007199254740993"`) para evitar perda de precisão nos bits menos significativos.
- Todos os SDKs também rejeitam `NaN`, `Infinity` / `-Infinity`, elementos nulos em listas e objetos/arrays aninhados dentro de propriedades de lista antes do enfileiramento.

### 2.3 Operações de Perfil de Usuário `$user_*`

Todos os SDKs fornecem 7 métodos padrão de mutação de perfil de usuário direcionados para a tabela de chave primária `abi.dim_users` do StarRocks:

| Método do SDK | `event_name` na Rede | Semântica de Mutação do Perfil |
|------------|-------------------|----------------------------|
| `userSet(props)` | `$user_set` | Sobrescreve as propriedades mais recentes do perfil do usuário (insere se não existir, atualiza se existir) |
| `userSetOnce(props)` | `$user_set_once` | Inicializa propriedades do perfil do usuário apenas se estiverem atualmente nulas (por exemplo, primeiro canal de aquisição, fonte de registro) |
| `userAdd(props)` | `$user_add` | Incrementa/decrementa atomicamente propriedades numéricas do perfil do usuário (por exemplo, pontos de fidelidade, gasto acumulado) |
| `userUnset(keys)` | `$user_unset` | Remove colunas de propriedades de perfil especificadas (`NULL` em `dim_users`) |
| `userAppend(props)` | `$user_append` | Adiciona elementos a propriedades de perfil de tipo array/lista |
| `userUniqAppend(props)` | `$user_uniq_append` | Adiciona elementos a propriedades de perfil de tipo array/lista com desduplicação automática |
| `userDelete()` | `$user_del` | Exclui a linha de perfil do usuário atual de `abi.dim_users` (`StarRocksSinkOP.DELETE`) preservando eventos comportamentais históricos em `dwd_events` |

> **Regra de Isolamento**: Ao construir eventos `$user_*` (ou `#user_*`), os SDKs **nunca injetam** Super Propriedades estáticas/dinâmicas ou propriedades de ambiente predefinidas (`$os`, `$app_version`, `$lib`), evitando que metadatos de ambiente poluam a tabela `abi.dim_users`.

### 2.4 Guia para Engenheiros de Integração: Requisitos de Campos e Responsabilidades Cliente vs. Servidor (Importante)

Em arquiteturas de produção, os **SDKs do lado do cliente (Web / MiniProgram / App Mobile)** e os **SDKs do lado do servidor (Go / Java)** operam em topologias de rede fundamentalmente diferentes. Os engenheiros de integração devem atentar para a diferença de responsabilidades dos campos em cada cenário:

| Campo / Propriedade | SDKs de Cliente (`ts-web` / `mobile` Flutter·Android·iOS) | SDKs de Servidor (`go` / `java` / `python` / `nodejs` / `csharp` / `php` / `ruby`) | HTTP Direto (`RESTFUL_API.md`) | Comportamento no Gateway (`:8081`) e Flink ETL |
| :--- | :--- | :--- | :--- | :--- |
| **`project_id` e `project_token`** | **Obrigatório uma vez no `init()`** | **Obrigatório ao inicializar o Consumer** | **Obrigatório no nível superior de cada requisição** | O gateway valida o status do projeto e o token; retorna `401/403` se inválido |
| **`event_name`** | **Obrigatório em cada `track()`** (definido automaticamente como `$user_*` por `userSet*()`) | **Obrigatório em cada `Track()`** (definido automaticamente como `$user_*` por `UserSet*()`) | **Obrigatório em cada evento** | Validado contra `<= 128` caracteres e `^[A-Za-z_][A-Za-z0-9_]*$` (ou lista permitida do sistema `$`/`#`) |
| **Identidade do Usuário (`distinct_id` / `login_id`)** | **Gerenciado automaticamente (não passado por `track`)**: o SDK gera e persiste automaticamente o `distinct_id` do visitante no `init()`; o desenvolvedor chama `login(accountId)` para persistir `login_id` localmente (os eventos seguintes incluem ambos os IDs automaticamente) | **Obrigatório em CADA chamada**: o SDK do servidor é um singleton sem estado compartilhado entre todos os usuários; o desenvolvedor **deve passar explicitamente** `login_id` (`accountId`) e/ou o `distinct_id` de visitante encaminhado pelo cliente (pelo menos um não vazio; nunca copie `login_id` para `distinct_id`) | **Obrigatório em cada evento** (pelo menos um entre `distinct_id` / `login_id` deve ser não vazio) | O gateway rejeita identidades vazias (`missing_identity`); sempre que um evento incluir tanto `distinct_id` quanto `login_id` não vazios, o Flink une-os automaticamente em `abi.identity_map` |
| **IP Público do Usuário Final (`#ip` / `$ip`)**<br/>*(Usado para GeoIP de País / Província / Cidade)* | **NÃO enviar (o cliente não pode obter)**: Navegadores e apps móveis operam atrás de NAT e não conseguem ler seu IP público de forma confiável; o Gateway extrai automaticamente o IP do cliente da conexão HTTP | **DEVE ser enviado pelo Servidor**: Quando backends Go/Java chamam o gateway, o IP da conexão TCP visto pelo gateway é o **IP do IDC/VPC do backend** (ou nenhum no caso do `LoggerConsumer`). Os engenheiros de servidor devem extrair o IP real do usuário dos cabeçalhos da requisição do cliente (`X-Forwarded-For` / `X-Real-IP`) e passá-lo em `properties["#ip"]` ou `"$ip"` | Omitir para chamadas diretas de clientes; **enviar `"#ip"` ou `"$ip"` em `properties` para chamadas de servidor para servidor** | O Flink resolve o GeoIP usando prioridade rigorosa **`properties["#ip"]` > `properties["$ip"]` > IP do socket do Gateway `client_ip`**, valida strings de IP numéricas e remove `#ip`/`$ip` de `properties` |
| **Carimbo de Data/Hora do Evento (`timestamp` / `#time` / `$time`)** | **Preenchido automaticamente (`Date.now()`)**: Omitir para eventos em tempo real; passar apenas `#time` / `$time` ou `options.timestamp` ao reprocessar eventos históricos offline | **Preenchido automaticamente em tempo real / Obrigatório para assíncrono e backfill**: Para consumidores atrasados de MQ, webhooks de pagamento ou backfill histórico, passe explicitamente a data/hora real de negócio via `properties["#time"]` (ou `TrackOptions.Timestamp` / `Date` / `Instant`) | **Obrigatório em cada evento** (seja no nível superior em ms `timestamp` ou em `properties["#time"]` / `"$time"`) | Os SDKs e o Gateway extraem `#time` / `$time` para o `timestamp` em ms do nível superior e removem-nos de `properties`; verificado contra `ts_window_days` |
| **Chave de Idempotência (`event_id`)** | **Gerado automaticamente (UUIDv4)**: Preservado automaticamente em repetições offline; de acordo com o controle D7① / G6, `trackFirst`/`trackUpdate`/`trackOverwrite` não são suportados na versão atual | **Gerado automaticamente por padrão / Recomendado para transações**: Envie uma chave de negócio determinística (por exemplo, `"ord_paid_" + orderNo`) via `TrackWithOptions` / `trackWithId` para evitar contagem duplicada em repetições de MQ | Recomendado (o Gateway gera um UUID se omitido, mas repetições sem um `event_id` fixo não serão desduplicadas) | O StarRocks `dwd_events` usa `event_id` para desduplicação idempotente |
| **Contexto do Dispositivo (`$os` / `$app_version` / `$screen_width`, etc.)** | **Coletado e injetado automaticamente pelo SDK** (apenas em eventos comportamentais; excluído de `$user_*`) | **Não disponível no servidor**: Defina metadados do serviço via `SetSuperProperties` ou encaminhe cabeçalhos do cliente (`$os`, `$app_version`, `$device_model`) em `properties` | Passar explicitamente em `properties` conforme necessário | O Flink promove `$os`, `$app_version`, `$device_model`, etc. para colunas físicas em `dwd_events` |

> **Melhor Prática para Vinculação de Funis Frontend + Backend**: Ao combinar navegação no cliente (SDK Web/App) com execução de pedidos no backend (SDK Go/Java/Python/Node/C#/PHP/Ruby), envie o ID de visitante do cliente (`abi.getDistinctId()`) para a API do seu backend (por exemplo, via cabeçalho `X-ABI-Distinct-Id`) e faça com que o backend passe o `loginId` (`accountId`), o `distinctId` do visitante encaminhado e o IP real do usuário `"#ip"` ao chamar o SDK de Servidor. O Flink unifica automaticamente ambos os IDs em qualquer evento, garantindo atribuição contínua de funil cross-device e geolocalização precisa.

## 3. Demonstrações Interativas em Duas Etapas e Referência Rápida de Exemplos de Código
