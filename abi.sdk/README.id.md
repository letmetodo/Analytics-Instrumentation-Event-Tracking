# Rangkaian SDK Pengumpulan Data Multibahasa ABI (`abi.sdk`)

**Bahasa / Language / ภาษา**: [简体中文](README.md) | [繁體中文](README.zh-TW.md) | [English](README.en.md) | [日本語](README.ja.md) | [한국어](README.ko.md) | [Español](README.es.md) | [Português](README.pt.md) | [Deutsch](README.de.md) | [Français](README.fr.md) | [Русский](README.ru.md) | [Tiếng Việt](README.vi.md) | [ไทย](README.th.md) | **[Bahasa Indonesia](README.id.md)**

`abi.sdk` menyediakan rangkaian SDK pengumpulan data sisi klien dan server kelas produksi untuk platform Analisis Perilaku Pengguna (UBA) & Business Intelligence (BI) ABI. Ditolok ukur terhadap [spesifikasi ThinkingData SDK v3.4](https://docs.thinkingdata.cn/ta-manual/v3.4/installation/installation_menu/installation_menu.html), rangkaian ini secara ketat menyelaraskan kontrak transmisi jaringan (wire contract), pemetaan identitas ganda (dual-identity mapping), dan validasi skema dengan Ingestion Gateway ABI [`abi.srv`](../abi.srv/) (`:8081`) serta mesin streaming [`abi.flink`](../abi.flink/) (Job1 real-time ETL & Job2 ingesti ODS mentah).

## 2. Kontrak Wire Batch Gateway Ingesti (`POST /collect/api/v1/track/batch`)

Seluruh konsumen HTTP klien dan server mengirimkan muatan batch JSON berformat standar ke gateway ingesti:

```json
{
  "project_id": 1,
  "project_token": "abi_tok_...",
  "debug": false,
  "dry_run": false,
  "events": [
    {
      "event_id": "018f6b9c-7c40-7000-8000-000000000001",
      "event_name": "OrderPaid",
      "distinct_id": "vis_device_001",
      "login_id": "user_10001",
      "timestamp": 1731174000000,
      "properties": {
        "$lib": "abi-ios-sdk",
        "$lib_version": "1.0.0",
        "$os": "iOS",
        "$app_version": "2.1.0",
        "$duration": 12.345,
        "amount": 199.0,
        "order_id": "9007199254740993"
      }
    }
  ]
}
```

### 2.1 Batasan Dual-ID & Idempotensi Selaras dengan ThinkingData

- **`distinct_id` (Visitor / Device ID)**: Pengidentifikasi tunggal pengunjung atau perangkat klien pada transmisi jaringan. Karakter kontrol ASCII (`0x00–0x08`, `0x0E–0x1F`, `0x7F`) akan ditolak, spasi awal/akhir Unicode dipangkas, dan panjang maksimum UTF-8 adalah **64 bita**. SDK klien menghasilkan dan menyimpan `distinct_id` secara lokal secara otomatis (dapat ditimpa melalui `identify(visitorId)`); SDK server dapat mengirim string kosong `""` saat melaporkan event tingkat akun murni yang telah memiliki `login_id` yang tidak kosong (**jangan pernah menyalin atau memotong `login_id` ke dalam `distinct_id`**).
- **`login_id` (Authenticated Account ID)**: Pengidentifikasi akun bisnis yang terautentikasi; panjang maksimum UTF-8 adalah **128 bita** (dikosongkan atau `""` untuk pengunjung yang belum masuk). Pada setiap event, **setidaknya salah satu** dari `distinct_id` atau `login_id` harus tidak kosong.
- **`login()` Lokal Murni pada Klien & Pemetaan ID Otomatis di Flink**: Memanggil `login(accountId)` pada SDK klien **hanya memperbarui `login_id` dalam status lokal** tanpa menimpa `distinct_id` dan tanpa memancarkan event sistem pengikatan identitas terpisah; memanggil `logout()` membersihkan `login_id` sembari mempertahankan `distinct_id` saat ini. Di seluruh SDK klien maupun server, **kapan pun suatu event perilaku (`Track*`) atau operasi profil (`$user_*`) membawa `distinct_id` dan `login_id` yang keduanya tidak kosong**, Flink Job1 secara otomatis merekonsiliasi keduanya dalam `abi.identity_map` secara real-time.
- **`event_id` (Kunci Utama Idempoten / Idempotent Primary Key)**: Panjang maksimum UTF-8 adalah **64 bita**. Dipertahankan di seluruh percobaan ulang offline saat terjadi kegagalan jaringan, HTTP `429`, atau respons `5xx` guna menjamin ingesti yang idempoten tanpa duplikasi (*Catatan: Berdasarkan gerbang D7① / G6, deduplikasi trackFirst serta event mutabel trackUpdate/trackOverwrite ditandai tidak didukung pada versi saat ini; untuk idempotensi teruskan nilai event_id tetap yang deterministik dalam track di jendela partisi yang sama*).

### 2.2 Perlindungan Presisi Integer Besar ($> 2^{53}-1$)

JavaScript dan parser JSON standar menggunakan angka floating-point presisi ganda IEEE-754 dengan batas integer aman maksimum sebesar $2^{53}-1$ (`9007199254740991`).

- Kapan pun nilai absolut dari properti integer melebihi `9007199254740991` (misalnya, ID pesanan Snowflake 64-bit seperti `9007199254740993` atau `Int64.min` / `Long.MIN_VALUE`), setiap SDK ABI secara otomatis mengonversinya menjadi string desimal (`"9007199254740993"`) untuk mencegah pemotongan bit rendah.
- Seluruh SDK juga menolak nilai `NaN`, `Infinity` / `-Infinity`, elemen daftar `null`, serta objek/array bersarang di dalam properti bertipe daftar sebelum dimasukkan ke dalam antrean.

### 2.3 Operasi Profil Pengguna `$user_*`

Seluruh SDK menyediakan 7 metode mutasi profil pengguna standar yang diarahkan ke tabel primary-key StarRocks `abi.dim_users`:

| Metode SDK | `event_name` pada Wire | Semantik Mutasi Profil Pengguna |
|------------|------------------------|---------------------------------|
| `userSet(props)` | `$user_set` | Menimpa properti profil pengguna terbaru (sisipkan jika belum ada, perbarui jika sudah ada) |
| `userSetOnce(props)` | `$user_set_once` | Menginisialisasi properti profil pengguna hanya jika saat ini bernilai kosong/null (misalnya, saluran akuisisi pertama, sumber pendaftaran) |
| `userAdd(props)` | `$user_add` | Menambah atau mengurangi properti numerik profil pengguna secara atomik (misalnya, poin loyalitas, total pengeluaran kumulatif) |
| `userUnset(keys)` | `$user_unset` | Menghapus kolom properti profil pengguna yang ditentukan (`NULL` di `dim_users`) |
| `userAppend(props)` | `$user_append` | Menambahkan elemen ke dalam properti profil pengguna bertipe larik/daftar |
| `userUniqAppend(props)` | `$user_uniq_append` | Menambahkan elemen ke dalam properti profil pengguna bertipe larik/daftar dengan deduplikasi otomatis |
| `userDelete()` | `$user_del` | Menghapus baris profil pengguna saat ini dari `abi.dim_users` (`StarRocksSinkOP.DELETE`) dengan tetap mempertahankan riwayat event perilaku di `dwd_events` |

> **Aturan Isolasi (Isolation Rule)**: Saat menyusun event `$user_*` (atau `#user_*`), SDK **tidak pernah menyuntikkan** Super Properties statis/dinamis atau properti lingkungan bawaan (`$os`, `$app_version`, `$lib`), guna mencegah metadata lingkungan mencemari `abi.dim_users`.

### 2.4 Panduan Insinyur Integrasi: Persyaratan Field & Tanggung Jawab Klien vs. Server (Penting)

Dalam arsitektur produksi, **SDK Klien (Web / Mini-Program / Aplikasi Seluler)** dan **SDK Server (Go / Java)** beroperasi dalam topologi jaringan yang sangat berbeda. Insinyur integrasi harus memperhatikan perbedaan tanggung jawab field di berbagai skenario:

| Field / Properti | SDK Klien (`ts-web` / `mobile` Flutter·Android·iOS) | SDK Server (`go` / `java` / `python` / `nodejs` / `csharp` / `php` / `ruby`) | HTTP Langsung (`RESTFUL_API.md`) | Perilaku Gateway (`:8081`) & Flink ETL |
| :--- | :--- | :--- | :--- | :--- |
| **`project_id` & `project_token`** | **Wajib satu kali saat `init()`** | **Wajib saat menginisialisasi Consumer** | **Wajib di tingkat atas setiap permintaan** | Gateway memvalidasi status proyek & token; mengembalikan `401/403` jika tidak valid |
| **`event_name`** | **Wajib pada setiap `track()`** (otomatis diatur ke `$user_*` oleh `userSet*()`) | **Wajib pada setiap `Track()`** (otomatis diatur ke `$user_*` oleh `UserSet*()`) | **Wajib pada setiap event** | Divalidasi dengan panjang `<= 128` karakter dan sesuai pola `^[A-Za-z_][A-Za-z0-9_]*$` (atau daftar putih sistem `$`/`#`) |
| **Identitas Pengguna (`distinct_id` / `login_id`)** | **Dikelola otomatis (tidak diteruskan per `track`)**: SDK otomatis menghasilkan & menyimpan visitor `distinct_id` saat `init()`; pengembang memanggil `login(accountId)` untuk menyimpan `login_id` secara lokal (event selanjutnya otomatis membawa kedua ID) | **Wajib pada SETIAP pemanggilan**: SDK Server adalah singleton tanpa status (stateless) yang digunakan bersama untuk semua pengguna; pengembang **wajib meneruskan secara eksplisit** `login_id` (`accountId`) dan/atau visitor `distinct_id` yang diteruskan klien (setidaknya satu tidak boleh kosong; jangan pernah menyalin `login_id` ke `distinct_id`) | **Wajib pada setiap event** (setidaknya salah satu dari `distinct_id` / `login_id` harus tidak kosong) | Gateway menolak event tanpa identitas (`missing_identity`); kapan pun event membawa `distinct_id` + `login_id` yang tidak kosong, Flink otomatis merekonsiliasi keduanya dalam `abi.identity_map` |
| **IP Publik Pengguna Akhir (`#ip` / `$ip`)**<br/>*(Digunakan untuk GeoIP Negara / Provinsi / Kota)* | **JANGAN diteruskan (Klien tidak dapat membacanya)**: Peramban web dan aplikasi seluler berada di balik NAT sehingga tidak dapat membaca IP publik dengan andal; Gateway secara otomatis mengekstrak IP klien dari koneksi HTTP | **WAJIB diteruskan oleh Server**: Saat backend Go/Java memanggil gateway, IP koneksi TCP yang dilihat gateway adalah **IP IDC/VPC backend** (atau tidak ada untuk `LoggerConsumer`). Insinyur server wajib mengekstrak IP asli pengguna dari header permintaan klien (`X-Forwarded-For` / `X-Real-IP`) dan meneruskannya dalam `properties["#ip"]` atau `"$ip"` | Kosongkan untuk panggilan klien langsung; **sertakan `"#ip"` atau `"$ip"` dalam `properties` untuk panggilan server-ke-server** | Flink menentukan GeoIP dengan urutan prioritas ketat: **`properties["#ip"]` > `properties["$ip"]` > soket `client_ip` Gateway**, memvalidasi literal IP, dan menghapus `#ip`/`$ip` dari `properties` |
| **Waktu Event (`timestamp` / `#time` / `$time`)** | **Diisi otomatis (`Date.now()`)**: Kosongkan untuk event real-time; teruskan hanya `#time` / `$time` atau `options.timestamp` saat melakukan backfill data offline masa lalu | **Diisi otomatis untuk real-time / Wajib untuk asinkron & backfill**: Untuk konsumen MQ tertunda, webhook pembayaran, atau pengisian data masa lalu, teruskan waktu bisnis aktual secara eksplisit melalui `properties["#time"]` (atau `TrackOptions.Timestamp` / `Date` / `Instant`) | **Wajib pada setiap event** (baik `timestamp` ms tingkat atas atau dalam `properties["#time"]` / `"$time"`) | SDK dan Gateway mengekstrak `#time` / `$time` ke dalam `timestamp` ms tingkat atas dan menghapusnya dari `properties`; diverifikasi terhadap jendela waktu `ts_window_days` |
| **Kunci Idempotensi (`event_id`)** | **Dihasilkan otomatis (UUIDv4)**: Dipertahankan secara otomatis di seluruh percobaan ulang offline; sesuai gerbang D7① / G6, `trackFirst`/`trackUpdate`/`trackOverwrite` dikonvergensikan sebagai tidak didukung dalam versi saat ini | **Dihasilkan otomatis secara default / Disarankan untuk transaksi finansial**: Teruskan kunci bisnis yang deterministik (misalnya, `"ord_paid_" + orderNo`) melalui `TrackWithOptions` / `trackWithId` untuk mencegah penghitungan ganda pada percobaan ulang MQ | Disarankan (Gateway membuat UUID jika dikosongkan, namun percobaan ulang tanpa `event_id` tetap tidak dapat dideduplikasi) | Tabel `dwd_events` StarRocks menggunakan `event_id` untuk deduplikasi idempoten |
| **Konteks Perangkat (`$os` / `$app_version` / `$screen_width`, dll.)** | **Dikumpulkan & disuntikkan otomatis oleh SDK** (hanya ke dalam event perilaku; dikecualikan dari `$user_*`) | **Tidak tersedia di server**: Atur metadata layanan melalui `SetSuperProperties`, atau teruskan header klien (`$os`, `$app_version`, `$device_model`) di dalam `properties` | Teruskan secara eksplisit di dalam `properties` sesuai kebutuhan | Flink mempromosikan `$os`, `$app_version`, `$device_model`, dll. menjadi kolom fisik di dalam `dwd_events` |

> **Praktik Terbaik Pengaitan Funnel Frontend + Backend (Frontend + Backend Funnel Stitching)**: Saat menggabungkan penjelajahan sisi klien (Web/App SDK) dengan penyelesaian pesanan sisi server (Go/Java/Python/Node/C#/PHP/Ruby SDK), teruskan ID pengunjung klien (`abi.getDistinctId()`) ke API backend Anda (misalnya melalui header permintaan `X-ABI-Distinct-Id`), dan pastikan backend meneruskan `loginId` (`accountId`), pengunjung `distinctId`, serta `"#ip"` nyata pengguna saat memanggil SDK Server. Flink akan mengaitkan kedua ID secara otomatis pada setiap event, memastikan atribusi funnel lintas-ujung yang mulus dan geolokasi yang akurat.

## 3. Demo Interaktif Dua Langkah & Referensi Cepat Contoh Kode

Seluruh demo antarmuka visual (UI) dan demo CLI / metode di seluruh `abi.sdk` mengikuti **Alur Kerja Dua Langkah (Two-Step Workflow)** yang seragam:
1. **Langkah 1 (Konfigurasi Parameter & Pratinjau JSON Permintaan Tunggal Langsung)**: Mengubah identitas, Super Properties, atau parameter event akan memperbarui **satu pratinjau konkret Request Body JSON `POST /collect/api/v1/track/batch`** secara langsung di tempat (tidak membanjiri layar dengan kartu log tanpa akhir).
2. **Langkah 2 (Konfirmasi & Pengiriman Eksplisit)**: Mengklik **Konfirmasi & Kirim** (`确认提交`) atau mengonfirmasi di CLI akan mengirimkan payload yang tepat tersebut dan menampilkan satu respons gateway terbaru.
