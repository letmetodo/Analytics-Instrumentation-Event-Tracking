# Suite de SDKs de Recolección de Datos Multilenguaje de ABI (`abi.sdk`)

**Idioma / Language**: [简体中文](README.md) | [繁體中文](README.zh-TW.md) | [English](README.en.md) | [日本語](README.ja.md) | [한국어](README.ko.md) | **[Español](README.es.md)** | [Português](README.pt.md) | [Deutsch](README.de.md) | [Français](README.fr.md) | [Русский](README.ru.md) | [Tiếng Việt](README.vi.md) | [ไทย](README.th.md) | [Bahasa Indonesia](README.id.md)

`abi.sdk` proporciona SDKs de recolección de datos de nivel de producción para clientes y servidores de la plataforma de Análisis de Comportamiento de Usuarios (UBA) y Business Intelligence (BI) de ABI. Tomando como referencia la [especificación ThinkingData SDK v3.4](https://docs.thinkingdata.cn/ta-manual/v3.4/installation/installation_menu/installation_menu.html), esta suite alinea estrictamente los contratos de transmisión (wire format), el mapeo de doble identidad y la validación de esquemas con la Pasarela de Ingesta ABI [`abi.srv`](../abi.srv/) (`:8081`) y los motores de streaming [`abi.flink`](../abi.flink/) (Job1 ETL en tiempo real y Job2 ingesta ODS sin procesar).

## 2. Contrato de Transmisión por Lotes de la Pasarela de Ingesta (`POST /collect/api/v1/track/batch`)

Todos los consumidores HTTP de cliente y servidor envían una carga útil JSON por lotes estandarizada a la pasarela de ingesta:

```json
{
  "project_id": 1,
  "project_token": "abi_tok_...",
  "debug": false,
  "dry_run": false,
  "events": [
    {
      "event_id": "018f6b9c-7c40-7000-8000-000000000001",
      "event_name": "OrderPaid",
      "distinct_id": "vis_device_001",
      "login_id": "user_10001",
      "timestamp": 1731174000000,
      "properties": {
        "$lib": "abi-ios-sdk",
        "$lib_version": "1.0.0",
        "$os": "iOS",
        "$app_version": "2.1.0",
        "$duration": 12.345,
        "amount": 199.0,
        "order_id": "9007199254740993"
      }
    }
  }
}
```

### 2.1 Restricciones de Doble Identidad e Idempotencia Alineadas con ThinkingData

- **`distinct_id` (ID de Visitante / Dispositivo)**: El único identificador de visitante o dispositivo cliente en tránsito. Se rechazan los caracteres de control ASCII (`0x00–0x08`, `0x0E–0x1F`, `0x7F`), se recortan los espacios en blanco Unicode iniciales y finales, y la longitud máxima en bytes UTF-8 es de **64 bytes**. Los SDKs de cliente generan automáticamente y persisten `distinct_id` localmente (modificable mediante `identify(visitorId)`); los SDKs de servidor pueden enviar una cadena vacía `""` al reportar eventos de cuenta pura que ya incluyen un `login_id` no vacío (**nunca copie ni trunque `login_id` en `distinct_id`**).
- **`login_id` (ID de Cuenta Autenticada)**: El identificador de cuenta de negocio autenticada; la longitud máxima en bytes UTF-8 es de **128 bytes** (se omite o envía `""` para visitantes no autenticados). Al menos uno de `distinct_id` o `login_id` **debe ser no vacío** en cada evento.
- **`login()` Puramente Local en Cliente y Mapeo Automático de IDs en Flink**: Llamar a `login(accountId)` en los SDKs de cliente **solo actualiza `login_id` en el estado local** sin sobrescribir `distinct_id` y sin emitir un evento del sistema de vinculación de identidad separado; llamar a `logout()` borra `login_id` conservando el `distinct_id` actual. En los SDKs de cliente y servidor, **siempre que cualquier evento de comportamiento (`Track*`) u operación de perfil (`$user_*`) incluya tanto `distinct_id` como `login_id` no vacíos**, Flink Job1 los vincula automáticamente en `abi.identity_map` en tiempo real.
- **`event_id` (Clave Primaria Idempotente)**: La longitud máxima en bytes UTF-8 es de **64 bytes**. Se conserva durante los reintentos sin conexión ante fallos de red, respuestas HTTP `429` o `5xx` para garantizar una ingesta idempotente. (*Nota: Según el control D7① / G6, la deduplicación con trackFirst y los eventos mutables trackUpdate/trackOverwrite no están soportados en la versión actual; para idempotencia, envíe un event_id determinista fijo en track dentro de la misma ventana de partición*).

### 2.2 Protección de Precisión para Enteros Grandes ($> 2^{53}-1$)

JavaScript y los analizadores JSON estándar utilizan números de coma flotante de doble precisión IEEE-754 con un entero seguro máximo de $2^{53}-1$ (`9007199254740991`).

- Siempre que el valor absoluto de una propiedad entera supere `9007199254740991` (por ejemplo, IDs de pedido Snowflake de 64 bits como `9007199254740993` o `Int64.min` / `Long.MIN_VALUE`), cada SDK de ABI lo serializa automáticamente como una cadena decimal (`"9007199254740993"`) para evitar el truncamiento de bits bajos.
- Todos los SDKs también rechazan `NaN`, `Infinity` / `-Infinity`, elementos nulos en listas y objetos/matrices anidados dentro de propiedades de lista antes de encolar.

### 2.3 Operaciones de Perfil de Usuario `$user_*`

Todos los SDKs proporcionan 7 métodos estándar de mutación de perfil de usuario enrutados a la tabla de clave primaria `abi.dim_users` de StarRocks:

| Método del SDK | `event_name` en Tránsito | Semántica de Mutación del Perfil |
|------------|-------------------|----------------------------|
| `userSet(props)` | `$user_set` | Sobrescribe las propiedades más recientes del perfil de usuario (inserta si no existe, actualiza si existe) |
| `userSetOnce(props)` | `$user_set_once` | Inicializa las propiedades del perfil de usuario solo si actualmente son nulas (por ejemplo, primer canal de adquisición, fuente de registro) |
| `userAdd(props)` | `$user_add` | Incrementa/decrementa atómicamente propiedades numéricas del perfil de usuario (por ejemplo, puntos de fidelidad, gasto acumulado) |
| `userUnset(keys)` | `$user_unset` | Borra columnas de propiedades de perfil de usuario especificadas (`NULL` en `dim_users`) |
| `userAppend(props)` | `$user_append` | Añade elementos a propiedades de perfil de usuario de tipo matriz/lista |
| `userUniqAppend(props)` | `$user_uniq_append` | Añade elementos a propiedades de perfil de usuario de tipo matriz/lista con deduplicación automática |
| `userDelete()` | `$user_del` | Elimina la fila de perfil del usuario actual de `abi.dim_users` (`StarRocksSinkOP.DELETE`) preservando los eventos históricos de comportamiento en `dwd_events` |

> **Regla de Aislamiento**: Al construir eventos `$user_*` (o `#user_*`), los SDKs **nunca inyectan** Superpropiedades estáticas/dinámicas ni propiedades preestablecidas del entorno (`$os`, `$app_version`, `$lib`), evitando que los metadatos del entorno contaminen `abi.dim_users`.

### 2.4 Guía para Ingenieros de Integración: Requisitos de Campos y Responsabilidades Cliente vs. Servidor (Importante)

En arquitecturas de producción, los **SDKs del lado del cliente (Web / MiniProgram / App Móvil)** y los **SDKs del lado del servidor (Go / Java)** operan en topologías de red fundamentalmente diferentes. Los ingenieros de integración deben prestar atención a cómo difieren las responsabilidades de los campos según el escenario del SDK:

| Campo / Propiedad | SDKs de Cliente (`ts-web` / `mobile` Flutter·Android·iOS) | SDKs de Servidor (`go` / `java` / `python` / `nodejs` / `csharp` / `php` / `ruby`) | HTTP Directo (`RESTFUL_API.md`) | Comportamiento en Pasarela (`:8081`) y Flink ETL |
| :--- | :--- | :--- | :--- | :--- |
| **`project_id` y `project_token`** | **Obligatorio una vez en `init()`** | **Obligatorio al inicializar el Consumer** | **Obligatorio en el nivel superior de cada solicitud** | La pasarela valida el estado y el token del proyecto; devuelve `401/403` si no es válido |
| **`event_name`** | **Obligatorio en cada `track()`** (asignado automáticamente a `$user_*` mediante `userSet*()`) | **Obligatorio en cada `Track()`** (asignado automáticamente a `$user_*` mediante `UserSet*()`) | **Obligatorio en cada evento** | Se valida contra `<= 128` caracteres y `^[A-Za-z_][A-Za-z0-9_]*$` (o lista permitida del sistema `$`/`#`) |
| **Identidad de Usuario (`distinct_id` / `login_id`)** | **Gestionado automáticamente (no se envía por `track`)**: el SDK genera automáticamente y persiste el `distinct_id` del visitante en `init()`; el desarrollador llama a `login(accountId)` para persistir `login_id` localmente (los eventos posteriores llevan ambos IDs de forma automática) | **Obligatorio en CADA llamada**: el SDK de servidor es un singleton sin estado compartido entre todos los usuarios; el desarrollador **debe pasar explícitamente** `login_id` (`accountId`) y/o el `distinct_id` de visitante reenviado desde el cliente (al menos uno no vacío; nunca copie `login_id` en `distinct_id`) | **Obligatorio en cada evento** (al menos uno de `distinct_id` / `login_id` debe ser no vacío) | La pasarela rechaza identidades vacías (`missing_identity`); siempre que un evento lleve tanto `distinct_id` como `login_id` no vacíos, Flink los vincula automáticamente en `abi.identity_map` |
| **IP Pública del Usuario Final (`#ip` / `$ip`)**<br/>*(Utilizada para GeoIP de País / Provincia / Ciudad)* | **NO enviar (el cliente no puede obtenerla)**: Los navegadores y apps móviles operan detrás de NAT y no pueden leer su IP pública de forma fiable; la pasarela extrae automáticamente la IP del cliente de la conexión HTTP | **DEBE ser enviada por el servidor**: Cuando los backends Go/Java llaman a la pasarela, la IP de la conexión TCP vista por la pasarela es la **IP del IDC/VPC del backend** (o ninguna para `LoggerConsumer`). Los ingenieros de servidor deben extraer la IP real del usuario de las cabeceras de la solicitud del cliente (`X-Forwarded-For` / `X-Real-IP`) y enviarla en `properties["#ip"]` o `"$ip"` | Omitir para llamadas directas de cliente; **enviar `"#ip"` o `"$ip"` en `properties` para llamadas de servidor a servidor** | Flink resuelve GeoIP utilizando la prioridad estricta **`properties["#ip"]` > `properties["$ip"]` > `client_ip` del socket de pasarela**, valida cadenas IP numéricas y elimina `#ip`/`$ip` de `properties` |
| **Marca de Tiempo del Evento (`timestamp` / `#time` / `$time`)** | **Completado automáticamente (`Date.now()`)**: Omitir para eventos en tiempo real; solo enviar `#time` / `$time` u `options.timestamp` al realizar cargas retrospectivas de eventos históricos fuera de línea | **Completado automáticamente para tiempo real / Obligatorio para asíncrono y backfill**: Para consumidores diferidos de MQ, webhooks de pago o backfill histórico, pase explícitamente el tiempo real del negocio mediante `properties["#time"]` (o `TrackOptions.Timestamp` / `Date` / `Instant`) | **Obligatorio en cada evento** (ya sea en el nivel superior en ms `timestamp` o en `properties["#time"]` / `"$time"`) | Los SDKs y la pasarela extraen `#time` / `$time` hacia el `timestamp` en ms de nivel superior y los eliminan de `properties`; se valida contra `ts_window_days` |
| **Clave de Idempotencia (`event_id`)** | **Generado automáticamente (UUIDv4)**: Se conserva automáticamente en reintentos fuera de línea; según el control D7① / G6, `trackFirst`/`trackUpdate`/`trackOverwrite` no están soportados en la versión actual | **Generado automáticamente por defecto / Recomendado para transacciones**: Pase una clave de negocio determinista (por ejemplo, `"ord_paid_" + orderNo`) mediante `TrackWithOptions` / `trackWithId` para evitar recuentos duplicados en reintentos de MQ | Recomendado (la pasarela genera un UUID si se omite, pero los reintentos sin un `event_id` fijo no se deduplicarán) | StarRocks `dwd_events` utiliza `event_id` para la deduplicación idempotente |
| **Contexto del Dispositivo (`$os` / `$app_version` / `$screen_width`, etc.)** | **Recolectado e inyectado automáticamente por el SDK** (solo en eventos de comportamiento; excluido de `$user_*`) | **No disponible en el servidor**: Configure metadatos del servicio mediante `SetSuperProperties`, o reenvíe cabeceras del cliente (`$os`, `$app_version`, `$device_model`) en `properties` | Enviar explícitamente en `properties` según sea necesario | Flink promueve `$os`, `$app_version`, `$device_model`, etc., a columnas físicas en `dwd_events` |

> **Mejor Práctica para Vincular Embudos Frontend + Backend**: Al combinar navegación del lado cliente (SDK Web/App) con procesamiento de órdenes en servidor (SDK Go/Java/Python/Node/C#/PHP/Ruby), envíe el ID de visitante del cliente (`abi.getDistinctId()`) a su API de backend (por ejemplo, mediante la cabecera `X-ABI-Distinct-Id`), y haga que el backend pase `loginId` (`accountId`), el `distinctId` del visitante reenviado y la IP real `"#ip"` del usuario al llamar al SDK de Servidor. Flink vincula automáticamente ambos IDs en cualquier evento, garantizando una atribución de embudo multicanal perfecta y geolocalización precisa.

## 3. Demostraciones Interactivas en Dos Pasos y Referencia Rápida de Ejemplos de Código

Todas las demostraciones visuales de interfaz de usuario y las demostraciones CLI/métodos en `abi.sdk` siguen un **Flujo de Trabajo en Dos Pasos** unificado:
1. **Paso 1 (Configuración de Parámetros y Vista Previa en Vivo del JSON de Solicitud Única)**: Al modificar la identidad, Superpropiedades o parámetros de eventos, se actualiza una **única vista previa concreta del JSON del cuerpo de la solicitud `POST /collect/api/v1/track/batch`** en el lugar (sin saturar con tarjetas de registro infinitas).
2. **Paso 2 (Confirmación Explícita y Envío)**: Al hacer clic en **Confirmar y Enviar** (`确认提交`) o confirmar en CLI, se envía esa carga útil exacta y se muestra la respuesta más reciente de la pasarela.
