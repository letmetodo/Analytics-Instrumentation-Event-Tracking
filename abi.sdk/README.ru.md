# Набор мультиязычных SDK для сбора данных ABI (`abi.sdk`)

**Язык / Language**: [简体中文](README.md) | [繁體中文](README.zh-TW.md) | [English](README.en.md) | [日本語](README.ja.md) | [한국어](README.ko.md) | [Español](README.es.md) | [Português](README.pt.md) | [Deutsch](README.de.md) | [Français](README.fr.md) | **[Русский](README.ru.md)** | [Tiếng Việt](README.vi.md) | [ไทย](README.th.md) | [Bahasa Indonesia](README.id.md)

Пакет `abi.sdk` предоставляет набор клиентских и серверных библиотек сбора данных промышленного уровня для платформы продуктовой аналитики поведения пользователей (UBA) и Business Intelligence (BI) ABI. Разработанный с ориентацией на спецификацию [ThinkingData SDK v3.4](https://docs.thinkingdata.cn/ta-manual/v3.4/installation/installation_menu/installation_menu.html), данный комплекс обеспечивает строгое соответствие форматов сетевых протоколов, сквозной двухуровневой идентификации пользователей и валидации схем данных с шлюзом сбора данных ABI [`abi.srv`](../abi.srv/) (`:8081`) и потоковыми движками [`abi.flink`](../abi.flink/) (Job1 — ETL в реальном времени и Job2 — сохранение сырых данных ODS).

## 2. Сетевой протокол пакетного приема данных шлюзом (`POST /collect/api/v1/track/batch`)

Все клиентские и серверные HTTP-консьюмеры отправляют на шлюз сбора стандартный пакетный JSON-запрос:

```json
{
  "project_id": 1,
  "project_token": "abi_tok_...",
  "debug": false,
  "dry_run": false,
  "events": [
    {
      "event_id": "018f6b9c-7c40-7000-8000-000000000001",
      "event_name": "OrderPaid",
      "distinct_id": "vis_device_001",
      "login_id": "user_10001",
      "timestamp": 1731174000000,
      "properties": {
        "$lib": "abi-ios-sdk",
        "$lib_version": "1.0.0",
        "$os": "iOS",
        "$app_version": "2.1.0",
        "$duration": 12.345,
        "amount": 199.0,
        "order_id": "9007199254740993"
      }
    }
  ]
}
```

### 2.1 Ограничения двойной идентификации и идемпотентности по стандарту ThinkingData

- **`distinct_id` (ID посетителя / устройства)**: единственный сетевой идентификатор посетителя или клиентского устройства. Управляющие символы ASCII (`0x00–0x08`, `0x0E–0x1F`, `0x7F`) отклоняются, начальные и конечные пробелы Unicode обрезаются, максимальная длина — **64 байта UTF-8**. Клиентские SDK автоматически генерируют и сохраняют `distinct_id` локально (может быть переопределен через `identify(visitorId)`); серверные SDK могут передавать пустую строку `""` при отправке чистых событий аккаунта с заполненным `login_id` (**ни в коем случае не копируйте и не усекайте `login_id` в `distinct_id`**).
- **`login_id` (ID авторизованного аккаунта)**: бизнес-идентификатор авторизованного пользователя; максимальная длина — **128 байт UTF-8** (опускается или передается как `""` для неавторизованных посетителей). По крайней мере один из идентификаторов `distinct_id` или `login_id` **обязан быть непустым** в каждом событии.
- **Локальный вызов `login()` в клиентских SDK и автоматическая склейка ID во Flink**: вызов `login(accountId)` в клиентских SDK **исключительно обновляет `login_id` в локальном состоянии**, не перезаписывая `distinct_id` и не отправляя системных событий связывания; вызов `logout()` очищает `login_id`, сохраняя текущий `distinct_id`. Во всех клиентских и серверных SDK: **когда любое поведенческое событие (`Track*`) или операция с профилем (`$user_*`) содержит одновременно непустые `distinct_id` и `login_id`**, Flink Job1 автоматически связывает их в таблице `abi.identity_map` в реальном времени.
- **`event_id` (Идемпотентный первичный ключ)**: максимальная длина — **64 байта UTF-8**. Сохраняется при повторных попытках отправки из офлайн-очереди при сбоях сети, HTTP `429` или `5xx`, обеспечивая идемпотентность приема. (*Примечание: в текущей версии согласно D7① / шлюзу G6 дедупликация trackFirst и изменяемые события trackUpdate/trackOverwrite не поддерживаются; для обеспечения идемпотентности передавайте детерминированный фиксированный event_id в track в пределах одного временного окна*).

### 2.2 Защита точности больших целых чисел ($> 2^{53}-1$)

JavaScript и стандартные парсеры JSON используют числа с плавающей точкой двойной точности IEEE-754, где максимальным безопасным целым числом является $2^{53}-1$ (`9007199254740991`).

- Если абсолютное значение целочисленного свойства превышает `9007199254740991` (например, 64-битные Snowflake ID заказов, такие как `9007199254740993` или `Int64.min` / `Long.MIN_VALUE`), каждый SDK ABI автоматически сериализует его в десятичную строку (`"9007199254740993"`), предотвращая потерю младших битов.
- Все SDK также отклоняют значения `NaN`, `Infinity` / `-Infinity`, элементы `null` внутри массивов и вложенные объекты/массивы внутри свойств-списков перед добавлением в очередь.

### 2.3 Операции с профилем пользователя `$user_*`

Все SDK предоставляют 7 стандартных методов изменения профиля пользователя, данные которых направляются в таблицу первичных ключей StarRocks `abi.dim_users`:

| Метод SDK | Сетевое имя `event_name` | Семантика изменения профиля |
|---|---|---|
| `userSet(props)` | `$user_set` | Перезапись актуальных свойств профиля пользователя (вставка при отсутствии, обновление при наличии) |
| `userSetOnce(props)` | `$user_set_once` | Однократная инициализация свойств профиля (только если поле в данный момент равно NULL, например, первый канал привлечения, источник регистрации) |
| `userAdd(props)` | `$user_add` | Атомарное увеличение/уменьшение числовых свойств профиля (например, баллы лояльности, накопленная сумма покупок) |
| `userUnset(keys)` | `$user_unset` | Сброс указанных колонок свойств профиля пользователя в `NULL` в таблице `dim_users` |
| `userAppend(props)` | `$user_append` | Добавление элементов в списочные/массивные свойства профиля пользователя |
| `userUniqAppend(props)` | `$user_uniq_append` | Добавление элементов в списочные свойства профиля пользователя с автоматической дедупликацией |
| `userDelete()` | `$user_del` | Удаление записи профиля пользователя из `abi.dim_users` (`StarRocksSinkOP.DELETE`) с сохранением исторических событий поведения в `dwd_events` |

> **Правило изоляции**: при формировании событий `$user_*` (или `#user_*`) SDK **никогда не внедряют** статические/динамические общие суперсвойства (Super Properties) или предустановленные системные параметры среды (`$os`, `$app_version`, `$lib`), предотвращая засорение таблицы `abi.dim_users` метаданными окружения.

### 2.4 Руководство для инженеров интеграции: требования к полям и разделение ответственности между клиентом и сервером (Важно)

В производственных архитектурах **клиентские SDK (Web / Мини-программы / Мобильные приложения)** и **серверные SDK (Go / Java / Python / Node / C# / PHP / Ruby)** работают в принципиально разных сетевых топологиях. Инженерам по интеграции необходимо учитывать различия в заполнении ключевых полей:

| Поле / Свойство | Клиентские SDK (`ts-web` / `mobile` Flutter·Android·iOS) | Серверные SDK (`go` / `java` / `python` / `nodejs` / `csharp` / `php` / `ruby`) | Прямой HTTP (`RESTFUL_API.md`) | Поведение шлюза (`:8081`) и ETL во Flink |
| :--- | :--- | :--- | :--- | :--- |
| **`project_id` и `project_token`** | **Обязательны один раз при `init()`** | **Обязательны при инициализации Consumer** | **Обязательны на верхнем уровне каждого запроса** | Шлюз проверяет статус проекта и токен; при невалидности возвращает `401/403` |
| **`event_name`** | **Обязательно при каждом `track()`** (автоматически выставляется в `$user_*` методами `userSet*()`) | **Обязательно при каждом `Track()`** (автоматически выставляется в `$user_*` методами `UserSet*()`) | **Обязательно в каждом событии** | Валидируется по длине `<= 128` символов и регулярному выражению `^[A-Za-z_][A-Za-z0-9_]*$` (или системному белому списку `$`/`#`) |
| **Идентификатор пользователя (`distinct_id` / `login_id`)** | **Управляется автоматически (не передается вручную в `track`)**: SDK автоматически генерирует и сохраняет `distinct_id` устройства при `init()`; разработчик вызывает `login(accountId)` для сохранения `login_id` локально (последующие события несут оба ID автоматически) | **ОБЯЗАТЕЛЬНО при КАЖДОМ вызове**: Серверный SDK является stateless-синглтоном, общим для всех пользователей; разработчик **обязан явно передать** `login_id` (`accountId`) и/или переданный от клиента `distinct_id` (хотя бы один непустой; никогда не копируйте `login_id` в `distinct_id`) | **Обязательно в каждом событии** (хотя бы один из `distinct_id` / `login_id` должен быть непустым) | Шлюз отклоняет события без идентификатора (`missing_identity`); при наличии обоих непустых `distinct_id` + `login_id` Flink автоматически связывает их в `abi.identity_map` |
| **Публичный IP пользователя (`#ip` / `$ip`)**<br/>*(Используется для GeoIP: страна / регион / город)* | **НЕ ПЕРЕДАВАТЬ (клиент не может его получить)**: браузеры и мобильные приложения находятся за NAT и не могут надежно определить публичный IP; шлюз автоматически извлекает IP из HTTP-соединения | **ОБЯЗАТЕЛЬНО передается сервером**: при запросах от бэкенда Go/Java IP TCP-соединения — это **IP дата-центра/VPC** (или отсутствует для `LoggerConsumer`). Инженер бэкенда обязан извлечь реальный IP пользователя из заголовков запроса (`X-Forwarded-For` / `X-Real-IP`) и передать в `properties["#ip"]` или `"$ip"` | Опускается для прямых вызовов с клиента; **передается в `properties["#ip"]` или `"$ip"` для межсерверных вызовов** | Flink определяет GeoIP по строгому приоритету: **`properties["#ip"]` > `properties["$ip"]` > сокетный `client_ip` шлюза**, проверяет IP и удаляет `#ip`/`$ip` из `properties` |
| **Временная метка события (`timestamp` / `#time` / `$time`)** | **Заполняется автоматически (`Date.now()`)**: опускается для событий реального времени; передается через `#time` / `$time` или `options.timestamp` только при ретроспективной загрузке исторических данных | **Автозаполнение для реалтайма / Обязательно для асинхронных задач и бэкфила**: при отложенной обработке MQ, вебхуках оплаты или исторической загрузке явно передавайте время бизнеса в `properties["#time"]` (или `TrackOptions.Timestamp` / `Date` / `Instant`) | **Обязательно в каждом событии** (либо ms `timestamp` на верхнем уровне, либо `properties["#time"]` / `"$time"`) | SDK и шлюз извлекают `#time` / `$time` в верхнеуровневый `timestamp` в мс и удаляют из `properties`; проверяется в пределах окна `ts_window_days` |
| **Ключ идемпотентности (`event_id`)** | **Генерируется автоматически (UUIDv4)**: автоматически сохраняется при повторных офлайн-попытках; по D7① / G6 операции `trackFirst`/`trackUpdate`/`trackOverwrite` унифицированы как неподдерживаемые | **Генерируется по умолчанию / Рекомендуется передавать для транзакций**: передавайте детерминированный бизнес-ключ (например, `"ord_paid_" + orderNo`) через `TrackWithOptions` / `trackWithId` для предотвращения дублей при повторах MQ | Рекомендуется (шлюз сгенерирует UUID, если поле опущено, но повторы без фиксированного `event_id` не дедуплицируются) | Таблица StarRocks `dwd_events` использует `event_id` для идемпотентной дедупликации |
| **Контекст устройства (`$os` / `$app_version` / `$screen_width` и др.)** | **Автоматически собирается и добавляется SDK** (только в события поведения; исключено из `$user_*`) | **Недоступно на сервере**: задавайте метаданные сервиса через `SetSuperProperties` или пробрасывайте заголовки клиента (`$os`, `$app_version`, `$device_model`) в `properties` | Передается явно в `properties` при необходимости | Flink переносит `$os`, `$app_version`, `$device_model` и другие свойства в физические колонки таблицы `dwd_events` |

> **Лучшая практика склейки воронок между фронтендом и бэкендом**: при объединении клиентского просмотра (Web/App SDK) и серверного оформления заказа (Go/Java/Python/Node/C#/PHP/Ruby SDK), передавайте идентификатор посетителя клиента (`abi.getDistinctId()`) в API вашего бэкенда (например, через заголовок `X-ABI-Distinct-Id`). Серверный код должен передавать как `loginId` (`accountId`), так и полученный `distinctId`, а также реальный `#ip` пользователя при вызове серверного SDK. Flink автоматически свяжет оба идентификатора при обработке любого события, обеспечивая сквозную аналитику воронки и корректную геолокацию.
