# ชุด SDK การเก็บรวบรวมข้อมูลหลายภาษาของ ABI (`abi.sdk`)

**ภาษา / Bahasa / Language**: [简体中文](README.md) | [繁體中文](README.zh-TW.md) | [English](README.en.md) | [日本語](README.ja.md) | [한국어](README.ko.md) | [Español](README.es.md) | [Português](README.pt.md) | [Deutsch](README.de.md) | [Français](README.fr.md) | [Русский](README.ru.md) | [Tiếng Việt](README.vi.md) | **[ไทย](README.th.md)** | [Bahasa Indonesia](README.id.md)

`abi.sdk` ให้บริการชุด SDK การเก็บรวบรวมข้อมูลทั้งฝั่งไคลเอนต์และเซิร์ฟเวอร์ระดับโปรดักชัน สำหรับแพลตฟอร์มการวิเคราะห์พฤติกรรมผู้ใช้ (UBA) และระบบข่าวกรองธุรกิจ (BI) ของ ABI โดยมีเกณฑ์มาตรฐานเทียบเท่ากับ [ข้อกำหนด ThinkingData SDK v3.4](https://docs.thinkingdata.cn/ta-manual/v3.4/installation/installation_menu/installation_menu.html) ชุด SDK นี้จัดวางสัญญาการส่งข้อมูลผ่านสาย (Wire Contract), การจับคู่ระบุตัวตนแบบสองชั้น (Dual-Identity Mapping), และการตรวจสอบสกีมาอย่างสอดคล้องกับ Ingestion Gateway ของ ABI [`abi.srv`](../abi.srv/) (`:8081`) และสตรีมมิงเอนจิน [`abi.flink`](../abi.flink/) (Job1 การทำ ETL แบบเรียลไทม์ และ Job2 การนำเข้า ODS แบบข้อมูลดิบ) อย่างเข้มงวด

## 2. สัญญาการส่งข้อมูลแบบแบตช์ของเกตเวย์นำเข้าข้อมูล (`POST /collect/api/v1/track/batch`)

ผู้บริโภค HTTP (HTTP Consumers) ทั้งฝั่งไคลเอนต์และเซิร์ฟเวอร์ทั้งหมดจะส่งเพย์โหลด JSON แบบแบตช์ที่เป็นมาตรฐานไปยังเกตเวย์นำเข้าข้อมูล:

```json
{
  "project_id": 1,
  "project_token": "abi_tok_...",
  "debug": false,
  "dry_run": false,
  "events": [
    {
      "event_id": "018f6b9c-7c40-7000-8000-000000000001",
      "event_name": "OrderPaid",
      "distinct_id": "vis_device_001",
      "login_id": "user_10001",
      "timestamp": 1731174000000,
      "properties": {
        "$lib": "abi-ios-sdk",
        "$lib_version": "1.0.0",
        "$os": "iOS",
        "$app_version": "2.1.0",
        "$duration": 12.345,
        "amount": 199.0,
        "order_id": "9007199254740993"
      }
    }
  ]
}
```

### 2.1 ข้อกำหนดด้านการระบุสองตัวตน (Dual-ID) และ Idempotency ตามแนวทาง ThinkingData

- **`distinct_id` (Visitor / Device ID)**: ตัวระบุผู้เยี่ยมชมหรืออุปกรณ์ฝั่งไคลเอนต์เพียงหนึ่งเดียวบนสายการส่ง อักขระควบคุม ASCII (`0x00–0x08`, `0x0E–0x1F`, `0x7F`) จะถูกปฏิเสธ, ช่องว่าง Unicode ที่นำหน้าหรือตามหลังจะถูกตัดออก, และความยาวไบต์ UTF-8 สูงสุดคือ **64 ไบต์** ไคลเอนต์ SDK จะสร้างและบันทึก `distinct_id` ภายในเครื่องโดยอัตโนมัติ (สามารถแทนที่ได้ผ่าน `identify(visitorId)`); ฝั่งเซิร์ฟเวอร์ SDK อาจส่งค่าว่าง `""` เมื่อรายงานอีเวนต์ระดับบัญชีล้วนที่มี `login_id` ที่ไม่ว่างอยู่แล้ว (**ห้ามคัดลอกหรือตัดทอน `login_id` ลงใน `distinct_id` โดยเด็ดขาด**)
- **`login_id` (Authenticated Account ID)**: ตัวระบุบัญชีธุรกิจที่ผ่านการรับรองความถูกต้องแล้ว; ความยาวไบต์ UTF-8 สูงสุดคือ **128 ไบต์** (ละเว้นหรือเป็น `""` สำหรับผู้เยี่ยมชมที่ยังไม่ได้เข้าสู่ระบบ) ในทุกอีเวนต์จะต้องมี **อย่างน้อยหนึ่งค่า** ระหว่าง `distinct_id` หรือ `login_id` ที่ไม่เป็นค่าว่าง
- **การเรียก `login()` ภายในเครื่องของไคลเอนต์อย่างแท้จริง และการแมป ID อัตโนมัติด้วย Flink**: การเรียกใช้ `login(accountId)` บนไคลเอนต์ SDK **จะอัปเดตเฉพาะ `login_id` ในสถานะภายในเครื่องเท่านั้น** โดยไม่เขียนทับ `distinct_id` และไม่ส่งอีเวนต์ระบบการผูกข้อมูลตัวตนแยกต่างหาก; การเรียก `logout()` จะล้างค่า `login_id` แต่ยังคงรักษา `distinct_id` ปัจจุบันไว้ สำหรับทั้งไคลเอนต์และเซิร์ฟเวอร์ SDK **เมื่อใดก็ตามที่อีเวนต์พฤติกรรม (`Track*`) หรือการดำเนินการโปรไฟล์ (`$user_*`) มีทั้ง `distinct_id` และ `login_id` ที่ไม่เป็นค่าว่างพร้อมกัน** Flink Job1 จะทำการผูกข้อมูลเข้าด้วยกันใน `abi.identity_map` แบบเรียลไทม์โดยอัตโนมัติ
- **`event_id` (คีย์หลักสำหรับการป้องกันข้อมูลซ้ำซ้อน / Idempotent Primary Key)**: ความยาวไบต์ UTF-8 สูงสุดคือ **64 ไบต์** ค่านี้จะถูกเก็บรักษาไว้เสมอแม้มีการลองส่งใหม่แบบออฟไลน์เมื่อเครือข่ายขัดข้อง หรือได้รับสถานะ HTTP `429` หรือ `5xx` เพื่อรับประกันว่าการนำเข้าข้อมูลจะเป็นแบบ Idempotent ไม่ซ้ำซ้อน (*หมายเหตุ: ตามเกณฑ์ D7① / G6 การกรองข้อมูลซ้ำด้วย trackFirst และอีเวนต์ที่แก้ไขได้ trackUpdate/trackOverwrite ถูกจัดให้ไม่รองรับในเวอร์ชันปัจจุบัน; สำหรับการทำงานแบบ Idempotent ให้ส่งค่า event_id คงที่ที่กำหนดไว้ล่วงหน้าใน track ภายในช่วงหน้าต่างพาร์ติชันเดียวกัน*)

### 2.2 การปกป้องความแม่นยำของจำนวนเต็มขนาดใหญ่ ($> 2^{53}-1$)

JavaScript และตัวแยกวิเคราะห์ JSON มาตรฐานใช้เลขทศนิยมความแม่นยำสองเท่าตามมาตรฐาน IEEE-754 ซึ่งมีขีดจำกัดจำนวนเต็มที่ปลอดภัยสูงสุดคือ $2^{53}-1$ (`9007199254740991`)

- เมื่อใดก็ตามที่ค่าสัมบูรณ์ของคุณสมบัติจำนวนเต็มเกินกว่า `9007199254740991` (เช่น รหัสคำสั่งซื้อ Snowflake แบบ 64 บิตอย่าง `9007199254740993` หรือ `Int64.min` / `Long.MIN_VALUE`) ทุก SDK ของ ABI จะแปลงค่านั้นเป็นสตริงฐานสิบ (`"9007199254740993"`) โดยอัตโนมัติ เพื่อป้องกันไม่ให้บิตต่ำสูญหายจากการตัดทอน
- ทุก SDK จะปฏิเสธค่า `NaN`, `Infinity` / `-Infinity`, สมาชิกในลิสต์ที่เป็น `null`, และอ็อบเจกต์/อาร์เรย์ที่ซ้อนกันภายในคุณสมบัติประเภทลิสต์ก่อนที่จะนำเข้าสู่คิว

### 2.3 การดำเนินการเกี่ยวกับโปรไฟล์ผู้ใช้ `$user_*`

ทุก SDK มีเมธอดมาตรฐาน 7 วิธีในการปรับเปลี่ยนโปรไฟล์ผู้ใช้ ซึ่งจะถูกส่งไปยังตารางคีย์หลัก `abi.dim_users` ใน StarRocks:

| เมธอดของ SDK | `event_name` บนสายส่ง | ความหมายการเปลี่ยนแปลงโปรไฟล์ |
|------------|-------------------|----------------------------|
| `userSet(props)` | `$user_set` | เขียนทับคุณสมบัติโปรไฟล์ผู้ใช้ล่าสุด (แทรกใหม่หากไม่มี, อัปเดตหากมีอยู่แล้ว) |
| `userSetOnce(props)` | `$user_set_once` | กำหนดค่าคุณสมบัติโปรไฟล์ผู้ใช้เฉพาะเมื่อปัจจุบันยังมีค่าว่าง (เช่น ช่องทางการได้มาครั้งแรก, แหล่งที่มาของการลงทะเบียน) |
| `userAdd(props)` | `$user_add` | เพิ่มหรือลดค่าคุณสมบัติโปรไฟล์ผู้ใช้ที่เป็นตัวเลขแบบอะตอมมิก (เช่น คะแนนสะสม, ยอดใช้จ่ายสะสม) |
| `userUnset(keys)` | `$user_unset` | ล้างคอลัมน์คุณสมบัติโปรไฟล์ผู้ใช้ที่ระบุให้เป็นค่าว่าง (`NULL` ใน `dim_users`) |
| `userAppend(props)` | `$user_append` | เพิ่มองค์ประกอบต่อท้ายคุณสมบัติโปรไฟล์ผู้ใช้ประเภทอาร์เรย์/ลิสต์ |
| `userUniqAppend(props)` | `$user_uniq_append` | เพิ่มองค์ประกอบต่อท้ายคุณสมบัติโปรไฟล์ผู้ใช้ประเภทอาร์เรย์/ลิสต์ พร้อมกรองค่าซ้ำออกโดยอัตโนมัติ |
| `userDelete()` | `$user_del` | ลบแถวโปรไฟล์ของผู้ใช้ปัจจุบันออกจาก `abi.dim_users` (`StarRocksSinkOP.DELETE`) โดยยังคงรักษาประวัติอีเวนต์พฤติกรรมใน `dwd_events` ไว้ตามเดิม |

> **กฎการแยกส่วน (Isolation Rule)**: เมื่อสร้างอีเวนต์ `$user_*` (หรือ `#user_*`) SDK **จะไม่แทรก** Super Properties แบบสแตติก/ไดนามิก หรือคุณสมบัติสภาพแวดล้อมที่ตั้งไว้ล่วงหน้า (`$os`, `$app_version`, `$lib`) เพื่อป้องกันไม่ให้ข้อมูลเมทาดาทาของสภาพแวดล้อมเข้าไปปนเปื้อนใน `abi.dim_users`

### 2.4 คู่มือสำหรับวิศวกรผู้ผสานการทำงาน: ข้อกำหนดของฟิลด์และความรับผิดชอบของ Client vs. Server (สำคัญมาก)

ในสถาปัตยกรรมระดับโปรดักชัน **SDK ฝั่งไคลเอนต์ (Web / มินิโปรแกรม / โมบายล์แอป)** และ **SDK ฝั่งเซิร์ฟเวอร์ (Go / Java)** ทำงานในโทโพโลยีเครือข่ายที่แตกต่างกันโดยสิ้นเชิง วิศวกรผู้ผสานการทำงานจะต้องให้ความสำคัญกับความแตกต่างของความรับผิดชอบของแต่ละฟิลด์ในแต่ละกรณี:

| ฟิลด์ / คุณสมบัติ | SDK ไคลเอนต์ (`ts-web` / `mobile` Flutter·Android·iOS) | SDK เซิร์ฟเวอร์ (`go` / `java` / `python` / `nodejs` / `csharp` / `php` / `ruby`) | ส่งตรงผ่าน HTTP (`RESTFUL_API.md`) | พฤติกรรมของ Gateway (`:8081`) และ Flink ETL |
| :--- | :--- | :--- | :--- | :--- |
| **`project_id` & `project_token`** | **ต้องระบุหนึ่งครั้งตอน `init()`** | **ต้องระบุเมื่อเริ่มต้นใช้งาน Consumer** | **ต้องระบุที่ระดับบนสุดของทุกคำขอ** | Gateway ตรวจสอบสถานะโปรเจกต์และโทเค็น; คืนค่า `401/403` หากไม่ถูกต้อง |
| **`event_name`** | **ต้องมีในทุกการเรียก `track()`** (ตั้งค่าเป็น `$user_*` อัตโนมัติเมื่อเรียก `userSet*()`) | **ต้องมีในทุกการเรียก `Track()`** (ตั้งค่าเป็น `$user_*` อัตโนมัติเมื่อเรียก `UserSet*()`) | **ต้องระบุในทุกอีเวนต์** | ตรวจสอบความยาว `<= 128` ตัวอักษรและตรงตาม `^[A-Za-z_][A-Za-z0-9_]*$` (หรือรายการที่อนุญาตระบบ `$`/`#`) |
| **ข้อมูลระบุตัวตนผู้ใช้ (`distinct_id` / `login_id`)** | **จัดการอัตโนมัติ (ไม่ต้องส่งต่อครั้งใน `track`)**: SDK สร้างและบันทึก visitor `distinct_id` อัตโนมัติเมื่อ `init()`; นักพัฒนาเรียก `login(accountId)` เพื่อบันทึก `login_id` ในเครื่อง (อีเวนต์หลังจากนั้นจะส่งทั้งสอง ID อัตโนมัติ) | **ต้องระบุในทุกการเรียก**: SDK เซิร์ฟเวอร์เป็นแบบ Stateless Singleton ที่ใช้ร่วมกันทุกผู้ใช้; นักพัฒนา **ต้องส่งอย่างชัดเจน** ทั้ง `login_id` (`accountId`) และ/หรือ visitor `distinct_id` ที่ส่งต่อมาจากไคลเอนต์ (ต้องมีอย่างน้อยหนึ่งค่าที่ไม่ว่าง; ห้ามคัดลอก `login_id` ใส่ `distinct_id`) | **ต้องมีในทุกอีเวนต์** (ต้องมีอย่างน้อยหนึ่งค่าระหว่าง `distinct_id` / `login_id` ที่ไม่ว่าง) | Gateway จะปฏิเสธอีเวนต์ที่ไม่มีข้อมูลระบุตัวตน (`missing_identity`); เมื่อใดก็ตามที่อีเวนต์มีทั้ง `distinct_id` + `login_id` ที่ไม่ว่าง Flink จะผูกข้อมูลเข้าด้วยกันใน `abi.identity_map` โดยอัตโนมัติ |
| **IP สาธารณะของผู้ใช้ปลายทาง (`#ip` / `$ip`)**<br/>*(ใช้สำหรับระบุ GeoIP ประเทศ / จังหวัด / เมือง)* | **ห้ามส่ง (ไคลเอนต์ไม่สามารถดึงค่านี้ได้)**: เบราว์เซอร์และแอปมือถือทำงานอยู่หลัง NAT จึงไม่สามารถอ่าน IP สาธารณะได้อย่างแม่นยำ; Gateway จะดึง client IP จากการเชื่อมต่อ HTTP โดยอัตโนมัติ | **ต้องส่งโดยเซิร์ฟเวอร์**: เมื่อแบ็กเอนด์ Go/Java เรียกไปยัง Gateway IP ของการเชื่อมต่อ TCP ที่ Gateway มองเห็นจะเป็น **IP ของ IDC/VPC แบ็กเอนด์** (หรือไม่มีเลยสำหรับ `LoggerConsumer`) วิศวกรเซิร์ฟเวอร์ต้องดึง IP จริงของผู้ใช้จากส่วนหัวของคำขอไคลเอนต์ (`X-Forwarded-For` / `X-Real-IP`) แล้วส่งมาใน `properties["#ip"]` หรือ `"$ip"` | ละเว้นสำหรับการเรียกจากไคลเอนต์โดยตรง; **ต้องส่ง `"#ip"` หรือ `"$ip"` ใน `properties` สำหรับการเรียกแบบ Server-to-Server** | Flink จะแปลง GeoIP ตามลำดับความสำคัญที่เข้มงวด: **`properties["#ip"]` > `properties["$ip"]` > ซ็อกเก็ต `client_ip` ของ Gateway**, ตรวจสอบความถูกต้องของเลข IP และตัด `#ip`/`$ip` ออกจาก `properties` |
| **เวลาของอีเวนต์ (`timestamp` / `#time` / `$time`)** | **เติมให้อัตโนมัติ (`Date.now()`)**: ละเว้นได้สำหรับอีเวนต์แบบเรียลไทม์; ส่งเฉพาะ `#time` / `$time` หรือ `options.timestamp` เมื่อต้องการย้อนรอยนำเข้าข้อมูลออฟไลน์ในอดีต | **เติมให้อัตโนมัติสำหรับเรียลไทม์ / จำเป็นสำหรับอะซิงโครนัสและการย้อนรอย**: สำหรับผู้บริโภค MQ ที่ล่าช้า เว็บฮุกการชำระเงิน หรือการย้อนรอยข้อมูลในอดีต ให้ระบุเวลาทางธุรกิจจริงผ่าน `properties["#time"]` (หรือ `TrackOptions.Timestamp` / `Date` / `Instant`) | **ต้องระบุในทุกอีเวนต์** (ระบุเป็น ms `timestamp` ที่ระดับบนสุด หรือใน `properties["#time"]` / `"$time"`) | SDK และ Gateway จะแยก `#time` / `$time` ออกมาเป็นมิลลิวินาที `timestamp` ที่ระดับบนสุดและตัดออกจาก `properties`; มีการตรวจสอบกับ `ts_window_days` |
| **คีย์ความแน่นอนของข้อมูล (`event_id`)** | **สร้างให้อัตโนมัติ (UUIDv4)**: เก็บรักษาไว้อัตโนมัติแม้ลองใหม่แบบออฟไลน์; ตามเกณฑ์ D7① / G6 การใช้ `trackFirst`/`trackUpdate`/`trackOverwrite` ถูกปรับเป็นไม่รองรับในเวอร์ชันปัจจุบัน | **สร้างให้อัตโนมัติเป็นค่าเริ่มต้น / แนะนำสำหรับธุรกรรมการเงิน**: ส่งคีย์ทางธุรกิจที่แน่นอน (เช่น `"ord_paid_" + orderNo`) ผ่าน `TrackWithOptions` / `trackWithId` เพื่อป้องกันการนับซ้ำเมื่อ MQ ลองใหม่ | แนะนำให้ระบุ (Gateway จะสร้าง UUID ให้หากละเว้น แต่การลองใหม่โดยไม่มี `event_id` คงที่จะไม่สามารถกรองซ้ำได้) | ตาราง `dwd_events` ของ StarRocks จะใช้ `event_id` ในการตัดข้อมูลซ้ำแบบ Idempotent |
| **บริบทของอุปกรณ์ (`$os` / `$app_version` / `$screen_width` ฯลฯ)** | **รวบรวมและแทรกให้อัตโนมัติโดย SDK** (เฉพาะในอีเวนต์พฤติกรรมเท่านั้น; ยกเว้นจาก `$user_*`) | **ไม่มีบนเซิร์ฟเวอร์**: ตั้งค่าข้อมูลเมทาดาทาของบริการผ่าน `SetSuperProperties` หรือส่งต่อส่วนหัวไคลเอนต์ (`$os`, `$app_version`, `$device_model`) ใน `properties` | ส่งอย่างชัดเจนใน `properties` ตามที่ต้องการ | Flink จะยกคุณสมบัติ `$os`, `$app_version`, `$device_model` ฯลฯ ขึ้นเป็นคอลัมน์ทางกายภาพใน `dwd_events` |

> **แนวทางปฏิบัติที่ดีที่สุดสำหรับการเชื่อมโยงฟันเนลระหว่างหน้าบ้านและหลังบ้าน (Frontend + Backend Funnel Stitching)**: เมื่อรวมการท่องเว็บฝั่งไคลเอนต์ (Web/App SDK) เข้ากับการทำรายการสำเร็จฝั่งเซิร์ฟเวอร์ (Go/Java/Python/Node/C#/PHP/Ruby SDK) ให้ส่ง ID ผู้เยี่ยมชมของไคลเอนต์ (`abi.getDistinctId()`) ไปยัง API แบ็กเอนด์ของคุณ (เช่น ผ่านส่วนหัว `X-ABI-Distinct-Id`) และให้แบ็กเอนด์ส่งทั้ง `loginId` (`accountId`), `distinctId` ของผู้เยี่ยมชม และ `"#ip"` จริงของผู้ใช้เมื่อเรียกใช้งาน SDK เซิร์ฟเวอร์ Flink จะผูก ID ทั้งสองเข้าด้วยกันโดยอัตโนมัติในทุกอีเวนต์ เพื่อให้มั่นใจว่าการระบุแหล่งที่มาของฟันเนลข้ามระบบและการระบุตำแหน่งทางภูมิศาสตร์เป็นไปอย่างแม่นยำไร้รอยต่อ

## 3. ตัวอย่างแบบโต้ตอบสองขั้นตอนและการอ้างอิงโค้ดตัวอย่างฉบับย่อ

การสาธิต UI เชิงภาพและการสาธิตผ่าน CLI / เมธอดทั้งหมดทั่วทั้ง `abi.sdk` จะปฏิบัติตาม **เวิร์กโฟลว์สองขั้นตอน (Two-Step Workflow)** ที่เป็นเอกภาพ:
1. **ขั้นตอนที่ 1 (กำหนดพารามิเตอร์และพรีวิว JSON ของคำขอเดี่ยวสด)**: การเปลี่ยนแปลงข้อมูลระบุตัวตน, Super Properties, หรือพารามิเตอร์ของอีเวนต์ จะอัปเดต **พรีวิว Request Body JSON ตัวจริงสำหรับ `POST /collect/api/v1/track/batch` เพียงอันเดียว** ในตำแหน่งเดิม (ไม่แสดงการ์ดบันทึกยาวเหยียดที่ไม่มีที่สิ้นสุด)
2. **ขั้นตอนที่ 2 (ยืนยันและส่งข้อมูลอย่างชัดเจน)**: การคลิก **ยืนยันและส่งข้อมูล** (`确认提交`) หรือการยืนยันใน CLI จะส่งเพย์โหลดที่แน่นอนนั้น และแสดงผลการตอบกลับล่าสุดเพียงรายการเดียวจากเกตเวย์
